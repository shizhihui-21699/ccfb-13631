# tesla-mcast:组播行情的 TESLA 式数据源认证

## 设计

针对「组播 + 高吞吐 + 丢包 + 防伪造 + 接收方不可冒充发送方」的约束,采用 TESLA(Timed Efficient Stream Loss-tolerant Authentication)变体:

```
密钥链:   K_0 ←H— K_1 ←H— ... ←H— K_N   (H = SHA-256,链尾随机,预生成)
时间槽:   每 100ms 一个槽 i,该槽所有包用 K_i 算 HMAC
数据包:   type | seq | interval | disclosed=K_{i-d} | HMAC | payload   (d=2)
检查点:   每 20 个槽对 (interval, K_i, t0, 参数) 做一次 Ed25519 签名,重复发 3 份
```

- **发送端开销**:每包 1 次 HMAC-SHA256(实测 ~0.76µs),签名每 2s 才 1 次(~13µs),摊销可忽略。
- **丢包容忍**:任何一把披露的 K_j 哈希 (j-i) 次即可验证更旧的 K_i。丢掉的披露由后面包里的钥匙一次性补回(链上跳跃前进),不需要重传。
- **防伪造**:接收端只在「本地槽 < 包槽 + d」时缓存包。攻击者看到披露的 K_j 时,j 槽窗口已关闭,用真旧钥匙造的包被时效检查直接拒绝;当前槽的钥匙尚未披露,无法伪造。
- **终端不可冒充发送端**:终端只持有公钥和已披露的旧钥匙,哈希链单向性保证推不出未披露的钥匙。
- **自举/迟到加入**:接收端钉住发送端公钥(带外分发),等下一个签名检查点即可上链,之后纯靠哈希链前进。

## 安全前提与边界

- 收发时钟松散同步:误差必须 << d×槽长(本配置 200ms,NTP ±10ms 足够)。
- 认证是**延迟**的:包先缓存,钥匙披露后才交付,固有延迟约 d~d+1 个槽(检查点会提前批量放行,实测平均 151ms)。需要即时认证的场景不适用。
- 防 DoS:单包诱导的链哈希次数上限 200k,缓存包数上限 200k。
- 链长 50 万槽 ≈ 13.9h;长跑用签名检查点平滑换链即可。

## 运行

```bash
cargo build --release
./target/release/tesla-mcast sender    --rate 20000          # 组播 239.255.42.99:5000
./target/release/tesla-mcast receiver  --drop 0.1 --duration 25   # 模拟 10% 丢包
./target/release/tesla-mcast attacker  --rate 2000           # 注入 4 类伪造包
```

(同机测试走 lo0 组播;`sender.pub` 为钉住的验证公钥,真实部署应带外分发。)

## 实测结果(Apple Silicon,20k pps,10% 模拟丢包,攻击者 2k pps 注入)

| 指标 | 数值 |
|---|---|
| 发送端吞吐 | 20,001 pkt/s 稳定 |
| 发送端每包认证开销 | HMAC 0.76µs(签名摊销 ~0.0003µs/包) |
| 接收端每包验证开销 | 0.72µs |
| 认证延迟(收包→验证交付) | 平均 151ms,最大 300ms |
| 隐含丢包率(seq 缺口) | 9.74%(≈注入的 10% 模拟丢包,真实丢包可忽略) |
| 收到的真包认证成功率 | 100%(丢包不影响幸存包的认证) |
| 伪造包通过数 | **0**(garbage/tamper → mac_fail;旧钥匙伪造 → stale;重放 → duplicate) |
